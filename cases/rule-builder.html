An anti-fraud rule builder analysts use without a developer

Fraud rules were written in an engineers' language, in a code field, so every rule waited for a developer. I proposed a visual builder on top of that language, kept the code view for those who knew it, and made the finished rule readable later.

Role
Lead Product Designer; the visual builder was my proposal
Product
ScanFraud, a B2B anti-fraud platform for payment providers
Timeline
May – Jun 2026
Scale
Builder (visual + code) · rule pages with version history

How do you want to read the case?

Every anti-fraud rule was a small program in an internal language, typed into a code field, so analysts who knew what to catch had to wait for a developer. I proposed a visual builder on top of the same language instead of replacing it: each condition is a card that reads like a sentence, the code view stays one click away, and where a rule applies is a separate step. A rule page shows the rule as a tree and as text, with version history. The builder has been live since mid-2026, and analysts build rules themselves.

01 · Context

          
Every rule went through a developer
  • Rules in code only
  • Ticket per change

          
An anti-fraud rule is a small program: if the total amount on this card today is above a limit, decline and notify. The engineers built their own language for it, and the only way to write a rule was a code field:

          
IF TOTAL_SUM(amount)
     WHERE card_hash == tx.card_hash
     INTERVAL calendar 24 hours > 5000

          
Analysts knew exactly what they wanted to catch, but couldn't write it themselves. Every new rule and every tweak became a ticket for a developer.

        

      


      

        

          
02 · Decision

          
Add a visual view, keep the code
  • Visual
  • Code
  • Same rule, two views

          
I proposed a visual builder on top of the language. The obvious move was to replace the code field. I kept it: people who had already learned the language shouldn't lose a tool that works for them.

          

            
Rejected
Replace the code field with a form. Simpler on paper, but it takes a working tool away from the people who use the product most.

            
Chosen
Two views of the same rule, Visual and Code. The switch between them is the whole migration path.

          

          
One trade-off stayed: an unfinished draft can’t be carried from one view to the other, so switching views resets it. Rather than hide that, the product warns before it happens.

        

        
      


      

        

          
03 · Decision

          
A rule made of blocks that read like a sentence
  • Function or parameter
  • Interval
  • WHERE
  • AND / OR

          
Each condition is a card. Its summary line says in words what the card does, and the fields below it are how you change it:

          
    
            
  • Function or parameter: a plain comparison (amount > 2500) or an aggregate (total sum of amount);
    • 
            
  • Interval: a calendar or rolling window, with an optional percentage threshold;
    • 
            
  • WHERE: which transactions count, such as the same card, the same customer, or a BIN country from a list;
    • 
            
  • AND / OR between cards, and the final comparison at the end.
    • 
          

          
Errors appear on the block that causes them, not in a banner above a long form. In a rule with five blocks, "something is wrong" is useless; "this interval needs a restriction" is not.

        

        
      


      

        

          
04 · Decision

          
What the rule does, separate from where it applies
  • Apply To
  • Merchants · services · terminals · providers

          
Scope is a second step: merchants, services, terminals and providers, linked with AND. The two are easy to confuse: narrowing the scope doesn't narrow what an aggregate counts. "Total sum on this card" still counts the card's transactions everywhere.

          
So the screen says it directly: Apply To chooses who gets the reaction or score; it doesn't change how functions are calculated.

        

        
      


      

        

          
05 · Decision

          
A rule you can read a month later
  • Condition tree
  • Plain rule text
  • Version history

          
Rules outlive the people who wrote them. The rule page shows the conditions as a tree next to the plain rule text with a Copy button, the entities it applies to, and a version history with a log for every change. Details are read-only; changes go through Edit in the header.

        

        
      


      

        

          
06 · Honest part

          
One exception to my own rule
  • Active toggle
  • Requested by heavy users
Conventions are defaults, not laws.
Note to self

          
In money-moving back-office screens I treat toggles in tables as an anti-pattern: one stray click shouldn't change something important. Yet the rules list has an Active toggle in every row.

          
It was a direct request from the heaviest users of the list: they switch rules on and off often and wanted to do it without opening each rule. So the toggle is a shortcut, not a silent switch. It opens the same activate/deactivate confirmation as the rule page, and a rule never changes state by accident.

          

            What I took from it
            
Conventions are defaults, not laws. This one was overridden by the people who use the screen most, and the risk it protects against is still covered.

          

        

        
      


      

        

          
07 · Result

          
What changed after
  • Rules without a ticket
  • Live since mid-2026
  • Code view kept

        

        

          
Rules without a ticket
Analysts, and anyone who works with the system day to day, open the builder and put a rule together themselves.

          
Live since mid-2026
The builder and rule pages shipped in summer 2026 and have been working and in steady use since. The product is live at scanfraud.com.

          
Nobody lost their tool
The code view is still there for those who prefer the language.

          
Rules stay readable
Tree, plain text and version history on every rule page.

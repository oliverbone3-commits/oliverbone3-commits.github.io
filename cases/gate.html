A payment gateway back-office where money never changes course on one click

The operators of a payment gateway connect merchants to providers, decide which payments go where and when the money moves between balances. I designed the gateway's back-office: payments as intent, transaction and operation, terminals and their routing rules, balances that transfer on a schedule, and the mapping of provider errors, all on one design system.

How do you want to read the case?

I was the only designer on a payment gateway's back-office, the tool its operators use to connect merchants to providers and move money between balances. Payments are shown as they work in the system: an intent, the transactions it took, the operations on them. Terminals are read-only until you press Edit, and routing restrictions are one canvas of allowed and restricted values instead of a list of single rules. Automatic transfers between balances dropped the toggle in the table for three named modes, a modal and a confirmation that says what will happen to the money. The rule behind all of it: changing where money goes must be explicit and confirmed; everything else should be quick and quiet.

01 · Context

Operators decide where merchants' money goes

  • Merchants
  • Providers
  • Terminals
  • Balances

A payment gateway sits between merchants and the providers that actually process their payments. Its back-office is where operators set that up: which merchant terminal talks to which provider terminal, under what contract, with which routing rules, and when money moves from one balance to another.

Most of that is everyday admin work. A few settings are not: in them an operator's mistake isn't a typo, it changes where a merchant's money goes. The back-office had to keep the first kind fast and make the second kind impossible to change by accident.

The principle

Changing a money flow must be explicit and confirmed. Everything else should be quick and quiet.

02 · Payments

A payment as the system sees it: intent, transaction, operation

  • Intents
  • Attempts & cascading
  • Operations
  • Drawer and full page

A buyer's attempt to pay is an intent. Behind it are the transactions it went through and the operations on them, such as a refund. The back-office shows payments in that order, with a tab for each, so an operator can start from what the merchant asked about and go down to what actually happened.

Lists open on status counters (success, pending, declined, refunded, action required), and active filters stay above the table as removable chips. A row opens in a drawer over the list: overview first, then additional parameters, anti-fraud result, payment instrument, customer and device. The payment log and a refund sit in the drawer's header.

The full intent page opens on Attempts & Cascading, because that is the first thing an operator needs when a merchant asks "what happened to this payment". One intent can take several attempts; when a provider declines, the payment can cascade to another provider terminal. The block shows each attempt with its transactions, each transaction with its provider terminal and operations such as a debit or a refund, and the status and time of every step, collapsed to the level the operator is looking at. Overview, parameters, anti-fraud, payment instrument, customer and device follow below, with a section index on the left.

03 · Balances

No toggles for money: named modes and a confirmation

  • Manual · Instant · Scheduled
  • Badge in the table
  • 10+ states

A toggle in a row is a money flow switched by a stray click.

Note to self

Money from a merchant's payments lands on one balance and has to move to the balance it's paid out from. The first idea was a toggle in the terminals table. It looked efficient, and that was the problem: one click in a row would switch a merchant's money flow.

The table only shows the mode as a badge and the next transfer time. Settings open in a modal, where technical names became three modes people understand: Manual, Instant and Scheduled, as radio cards with a line on what each one does. Scheduled takes run hours, a timezone, a threshold that flags unusually large transfers and a balance that always stays put, and the modal states when the next transfer will run.

The main button is always Save: a label that changed with the selection confused people. The meaning moved into the confirmation instead, and confirmations appear only when the money flow changes. Editing run hours doesn't ask "are you sure"; switching from Instant to Scheduled does, and says what happens to incoming payments in the meantime.

04 · Routing

One canvas of restrictions instead of rules one by one

  • Allowed · Restricted
  • 10 parameters
  • Priority and weight

Routing decides which provider terminal a payment goes to. The first version was a table of single rules: add one, edit one, delete one. In review with the product manager it became one canvas of restrictions grouped by type. For each type an operator picks Allowed or Restricted and fills the list: payment system, issuer, BIN country, BIN, customer email, card number, billing country, IP country, merchant customer ID. An amount range comes first, priority and weight close it.

Long lists stay manageable: values are chips, and "copy all" and "delete all" handle a whole list in one action. The modal wasn't drawn from scratch either. It was assembled from the existing rule-creation modal, and at the product manager's request the block moved into the main terminal screen instead of a separate section.

05 · Terminals and contracts

Read-only by default, overrides that inherit

  • Edit in the header
  • General + special terms
  • Empty field inherits

Detail pages became read-only: no toggles or checkboxes on them, edits go through Edit in the header. A merchant terminal page reads top to bottom: overview, checkout settings, URLs, authentication, API settings, cascading, anti-fraud settings, the provider terminals it's connected to and its contract history, with a section index on the left.

The same thinking shaped special fee terms in a terminal contract. On top of the general terms, operators override values for a specific payment system in five blocks: reserve, debit, credit, refund and chargeback, for the merchant side and the provider side. Each block has "General terms" and "Special terms"; an empty field inherits the general value, and view mode shows only what is overridden. Tabs per payment system were rejected: an override hidden in a tab is easy to miss.

06 · Errors

Every provider's decline codes, mapped to one internal set

  • Provider reason → internal reason
  • Processing and Public API

Each provider returns its own codes for the same problem. The mapping screen lists them next to the internal reason they become: provider, provider code and description on one side, internal name, code and description on the other. Creating or editing a mapping is one short modal; deleting one names the code it removes.

07 · Honest part

What went wrong

  • Drawing before looking
  • Rules one by one
  • A clever button label
  • Drawing before looking. Twice the product manager's review sent me back to an existing component. The routing modal ended up assembled from rule creation instead of drawn anew. Now I search the system before I draw.
  • Rules one by one. Routing restrictions started as a table of individual rules. After review they became one canvas by type and moved into the main terminal screen.
  • A clever button label. A main button whose text changed with the selected mode confused people. "Save" plus a confirmation that says what happens worked better.
